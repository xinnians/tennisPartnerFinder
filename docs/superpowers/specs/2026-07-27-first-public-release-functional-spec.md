# 台北網球球局平台 — 首次公開發布功能規格（修訂版）

## 文件狀態

本文件取代 `2026-07-27-tennis-partner-finder-first-version-functional-spec.md`（Codex 初稿）作為首次公開發布的實作依據；初稿保留為歷史紀錄。修訂依據：六視角比對分析（42 agent、36 論點對抗驗證）、四路市場研究（16 agent、雙來源覆核）、六路規格驗證（0 blocker、14 major 已全數修入），以及使用者 2026-07-27 的五項拍板。

### 拍板紀錄（2026-07-27，不再重議）

1. **聯絡模型：建球局群組聊天**，取代 LINE 交換；LINE 個人欄位走過渡退場。
2. **首發內容：依本規格修稿重排後，才進行第一次社群發布**（hosted 已部署+QA，尚無真實使用者）。
3. **在場狀態與球友目錄：保留並加觀察指標**（推翻初稿的延後/停用清單）；初稿的「我現在想打」機制因此不做。

5. **無地點球局的位置表達：候選球場清單（1~3 個）**，不用行政區、不用中心點半徑；廣播訂閱單位同步從行政區改為球場。

### 術語

沿用現行 UI 用語，本文與實作一致：**主揪**（host，即初稿的「發起人」）、**直接加入**（join_mode `instant`）、**審核加入**（join_mode `approval`）。**候選局**＝場地類型為「候選球場」的球局（本文簡稱，與「候選球場局」同義）。UI 既有文案不因本規格改名。

## 產品定位

幫助不依賴球團、俱樂部或既有熟人圈的網球玩家，更快找到合適球友，把時間、地點與人快速湊成一場球。

- 服務獨立約球的個人使用者，不作為球團、俱樂部或會員體系的管理工具。
- 首發公開範圍是**台北市、網球**；資料庫保留雙北球場目錄，但新北市球場不開放公開球局。擴區需要密度證據與獨立決策。
- 公開地圖只顯示一般使用者可發現、可加入的球局，不承載球團內部局或會員專用局。
- 不爬取、儲存或轉貼私人 LINE／Facebook 社群內容或身分資料（沿用既有邊界）。

## 核心體驗

1. **發起球局**：快速填寫資訊並發布邀約，可立即開打或預約未來。
2. **發現球局**：從地圖與清單找到附近、時間與程度合適的球局（含進行中、開打兩小時內仍可加入的局）。
3. **加入球局**：直接加入（預設）或經主揪審核；每人一個名額。名額湊滿即成局（候選球場局另需定案，見下）。
4. **群組溝通開打**：已確認參加者進入球局專屬群組聊天，協調集合、費用與臨時變動。

## 發起球局

### 場地類型（三型）

| 類型 | 場地 | 時間 | 備註 |
|---|---|---|---|
| 已訂場 | 單一球場 | 固定開始時間＋時長 | 可選填費用說明 |
| 現場等場 | 單一球場 | 集合時間＋預計時長，可標時間彈性 | 人滿＝球友湊齊，不保證取得場地；預設公共免費球場，不顯示場租 |
| 候選球場 | 勾選 2~3 個候選球場 | 日期＋可打時間範圍＋預計時長 | 主揪在範圍起點前**定案**單一球場與時間 → 系統通知參加者 |

- 球場一律出自球場目錄（`data/courts.json` 單一來源）；**不開放**使用者自行放置圖釘新增地點。目錄缺漏走回報／維運流程補齊。
- 球場資料維運面可逐步補充使用模式標註（預約制、現場輪流、並行、待確認）；此為目錄品質工作，非首發功能。

### 候選球場局的生命週期

- 候選局須勾選**至少 2 個**候選球場；只勾 1 個時，表單引導改用已訂場或現場等場型（已經決定的場地不需要定案流程）。
- **定案期限＝可打時間範圍起點**。範圍起點前 3 小時仍未定案，系統提醒主揪——**提醒只發一次**，通知深連結直達**一鍵定案**介面：候選球場一排按鈕、時間預設為範圍起點（可調），點一下完成，不是另一張表單。
- 範圍起點過後仍未定案 → 球局視同過期下架，並通知參加者（沿用既有 expire 機制，錨點為範圍起點）。
- 未定案期間的可發現／可加入窗口：至範圍起點為止。定案後取得固定開始時間，回歸一般窗口規則（開打後兩小時內仍可加入）。
- 開打前提醒只在定案後（取得固定時間）排程；定案本身另有即時通知。
- 型別收斂只走定案動作：候選局不可用一般編輯改成其他型（見「發起後的管理」）。

### 必填資訊

- 場地類型與對應的球場／候選清單。
- 時間（依類型：固定開始時間／集合時間／日期＋時間範圍）＋預計時長。
- 想怎麼打：單打、雙打，或到場再決定（UI 一律用「單打／雙打」，不用「賽制」這類正式稱呼）。
- 人數：主揪自動佔第一個名額，只填**還缺幾人**（1~3）。單打／雙打與缺額為**軟連動**：只用來帶入建議值（單打 1、雙打 3），主揪可自由調整，不做硬性驗證——場外朋友同行、多人輪打等情境都存在，缺額以主揪填的數字為準。不開放不限人數。
- 程度條件：本局接受的 NTRP 範圍。主揪個人 NTRP 未填時，建局表單就地引導先補自評值（資料庫層要求主揪 NTRP 已填才能建局）。

### 選填資訊

- 已訂場的費用說明（純文字資訊欄位，不涉金流）。
- 簡短說明。
- 加入方式：直接加入（預設）或審核加入。

## 地圖與球局發現

- 首頁以地圖為主，搭配可上拉的球局清單。

## 加入規則

- 主揪可選直接加入或審核加入；**直接加入為預設**，讓湊局更快。
- 程度配對優先由主揪設定的 NTRP 範圍處理；審核作為擔心自評不準或需額外確認時的例外保護。
- 加入分支一覽：

| 球局模式 | 加入者 NTRP | 行為 |
|---|---|---|
| 直接加入 | 已填且在範圍內 | 點「加入球局」立即成為已確認參加者 |
| 直接加入 | 未填 | 改為「申請加入」，就地提示「補填 NTRP，符合本局程度範圍即可不經審核加入」 |
| 直接加入 | 已填但在範圍外 | 改為「申請加入」，UI 註明「你的 NTRP 在本局範圍外」，由主揪裁量 |
| 審核加入 | 任何狀態 | 一律建立申請，主揪通過／未通過 |

- 審核只需通過或未通過，不要求拒絕原因；申請者收到中性結果通知。
- 加入前可見主揪及已確認參加者的暱稱、頭像與 NTRP（若有填）；此名單為**登入後可見**，匿名探索面維持現行最小欄位（主揪暱稱／NTRP／檔案完整旗標），不因此擴充。申請中資料只對申請者與主揪可見。
- 球局滿員只顯示「名額已滿」；**第一版不做候補名單**（初稿在此自相矛盾，統一為不做）。
- 每位使用者在同一球局只佔一個名額。

## 發起後的管理

- 主揪可**編輯球局資訊**、處理審核申請、定案候選球場，或取消整場；已有參加者時，變更會以系統訊息＋推播通知參加者，參加者可自行留下或取消，不要求重新確認。
- 編輯範圍（第一版）：
  - 可編輯：時間、球場（同型內更換）、缺額（不得低於已確認人數，資料庫層既有不變量）、NTRP 條件、單打／雙打（軟連動：僅重新帶入缺額建議值，不強制改缺額）、費用說明、簡短說明。
  - 不可編輯：場地類型（候選局收斂只走定案；已訂場↔等場不可互轉，要改請取消重開）、加入方式。
- 主揪可增加缺額；名額由滿變空時，地圖與詳情重新開放加入。
- 第一版不提供主揪單獨移除已確認參加者；球局無法繼續只能取消整場。
- 取消限開始前；參加者可隨時取消，名額立即釋出；主揪取消時全體參加者立刻收到通知（恆送，見通知表）。

## 球局群組聊天

### 範圍

- 加入成功後自動進入該球局的臨時群組；成員＝主揪＋已確認參加者。申請中、被婉拒、已退出者不可見群組內容（退出者離開群組）。
- 第一版只做：文字訊息、系統訊息（成員加入／退出、球局變更、候選定案）、參加者名單、置頂球局資訊卡。
- **封存觸發**：球局狀態進入 `cancelled`／`played`／`expired` 任一即封存；封存＝唯讀可回顧，不能再傳訊息。取消局的群組同樣唯讀保留，讓參加者看得到取消脈絡。
- 不做局外私訊、不做陌生人社群、不做貼圖／圖片（第一版純文字）。

### 讀寫通道（架構原則）

第一版**維持 view／RPC 唯一瀏覽器資料邊界**：訊息寫入走 RPC，讀取走 view，以「進入群組時載入＋推播帶動刷新＋回到前景刷新」的輪詢式體驗實作，不開放 browser 直接訂閱 raw 訊息表。Supabase Realtime 列為後續升級選項；屆時再議是否為訊息表開 RLS 直讀例外，並同步更新 CLAUDE.md 的邊界條文。

### 治理與隱私（本節是新的隱私契約，強度對齊既有資料庫層原則）

- **推播只送事件不送內容**：群組新訊息的推播 payload 只含「球局摘要＋有新訊息」，訊息本文永不進 push payload、outbox、log 或匿名面（沿用既有 payload allowlist 機制，新增事件型別）。群訊推播節流：同一群組 5 分鐘內至多一則（暫訂，上線前可調）。
- **訊息層檢舉**：可檢舉單則訊息與使用者；檢舉進人工佇列，**查證後**才限制發局／加入（修訂初稿的「先限制再查看」——單一檢舉自動限制會開出惡意檢舉凍結任意人的攻擊面）。
- **封鎖**：全域生效——互相看不到對方訊息、被封鎖者不能加入封鎖者開的局、不能對其發出邀請；被封鎖者也不會收到封鎖者在群組發言的推播。封鎖不回溯移除既有同局關係（名單仍互見），僅套用訊息互不可見與後續加入／邀請限制。
  **封鎖的隱蔽程度（2026-07-28 修訂）**：不主動通知對方，UI 也不揭露「你被封鎖了」——被封鎖者看到的是終局但中性的說明（例如「這個球局目前無法加入」）。但**不保證 wire 層不可推論**：被封鎖者永遠能觀察到「別人加得進、我加不進」，硬要讓 API 回應完全不可區分，代價是把真實錯誤情境一起模糊掉。因此中性只保證到 UI 層。封鎖清單（`my_player_blocks`）的暱稱僅在雙方有共同球局關聯或對方在球友目錄時顯示，其餘顯示佔位字樣，避免成為未 opt-in 使用者的暱稱列舉管道。
  **已知取捨（2026-07-28 驗收記錄）**：①暱稱遮罩只驗被封鎖者是否在目錄，不驗 viewer 自己是否達目錄門檻（與 `player_directory` 的互惠條件不對稱）——只填暱稱的登入者可逐一封鎖換回目錄成員暱稱；影響限於已 opt-in 者，Stage 5 的 migration 順帶補上 viewer 側門檻。②「共同球局關聯」不限 status 且 `declined`／`withdrawn` 列永久留存，因此解鎖是永久的，形成「此人是否曾出現在我參與過的任一球局」的推論管道；維持現狀。③封鎖不套用在生命週期推播（改局／定案／取消），被封鎖的參加者仍會收到該球局的異動通知——只有群聊發言的推播套過濾。
- **保存政策**：封存後 90 天刪除訊息內容（暫訂，上線前可調）；涉檢舉的訊息保留至結案。
- **LINE 過渡**：群聊上線後，個人檔案 LINE 欄位改為選填；`session_contacts` 揭露面保留一個過渡版本（已成局者不中斷聯絡），群聊穩定後退役。新註冊者不再被要求填 LINE。

## 通知

派送鏈沿用現行資產：outbox（service-only）＋ pg_cron 每分鐘 ＋ Edge Function ＋ Web Push（VAPID），payload allowlist 不變、新增事件型別。

| 事件 | 收件人 | 可否關閉 |
|---|---|---|
| 有新的加入申請 | 主揪 | 可 |
| 加入申請結果 | 申請者 | 可 |
| 收到球局邀請（沿用球友卡邀請） | 受邀者 | 可 |
| 球局變更 | 已確認參加者 | 可 |
| 候選定案 | 已確認參加者 | **恆送**（不可關） |
| 球局取消 | 已確認參加者 | **恆送**（不可關） |
| 群組新訊息 | 群組成員 | 可 |
| 開打前提醒（開打／集合前 1 小時，暫訂可調） | 已確認參加者 | 可 |
| **訂閱球場**有新球局（候選局＝任一候選球場命中） | 訂閱者 | 退訂該球場即停 |

- 定案與取消恆送的理由：關掉會讓參加者不知道場地定在哪、球局已取消；群聊系統訊息恆有，但不能假設人人會回來看。
- 廣播訂閱單位由行政區改為**球場多選**（上限暫訂 10 個）。行政區訂閱退場：舊表與 RPC 以 migration 移除、事件型別退役；通知設定頁顯示一次性重選提示（hosted 尚無真實使用者，遷移成本近零）。
- 候選局命中訂閱時的 payload：`court`＝命中訂閱的那個候選球場、`start_at`＝時間範圍起點；allowlist 語義不變，pgTAP 同步更新。
- 高匹配即推／每日摘要：**延後**（現行無 digest 基礎設施，首發用即時事件＋球場訂閱驗證留存假設即可）。

## 球友層：目錄與在場狀態（保留）

- 球友目錄（opt-in、authenticated-only）與在場狀態（互惠、前景限定、只存球場 court_id、TTL 3 小時、預設關閉）**維持上線**，並依 `2026-07-25-player-directory-off-map-redesign-design.md` 的方向改版：目錄轉列表、地圖只留「在線」（07-25 已把使用者可見文字「在場」改名「在線」）、邀請沿用球友卡。該設計已核可、前端尚未實作，工作量列入「調整」清單。
- 07-25「不可退讓」節的 `profile_courts`／常打球場必填條款，由本規格的檔案門檻鬆綁**取代**（目錄 opt-in 者仍要求常打球場，見門檻矩陣；以本規格為準）。
- 首發加入觀察指標：在線分享開啟人數、目錄 opt-in 人數、由球友卡發出的邀請數；以真實數據決定此層後續投資（拍板 3）。
- 「接受現場問候」維持現行。

## 個人檔案與信任安全

- Google 登入為主要方式；名稱與頭像帶入，確認或修改暱稱後即可進入地圖。
- 個人檔案：暱稱（必填）、頭像（Google 頭像或預設圖；**不做**自選照片上傳，避開審核義務）、NTRP（可跳過，之後隨時補填；未填的影響見加入規則）、簡短自介（選填）、LINE（過渡期選填，群聊穩定後退場，見治理與隱私節）。打法、時段、常打球場改為**選填**（供球友卡與配對加分，不再是參與門檻）。
- 門檻矩陣（資料庫層 gate，取代現行單一 `require_complete_profile`）：

| 動作 | 資料庫層要求 |
|---|---|
| 瀏覽地圖／球局 | 登入即可 |
| 加入球局（申請或直接加入） | 暱稱 |
| 建局 | 暱稱＋個人 NTRP |
| 球友目錄 opt-in | 暱稱＋NTRP＋至少一個台北市常打球場 |
| 在線分享 opt-in | 暱稱＋NTRP |
| 發出邀請 | 同建局 |

  `session_discovery` 的 `host_profile_complete` 欄位保留欄名，語義改為「暱稱＋NTRP 已填」（隨 discovery 契約一次性改版，見對照節）。
- 不公開電話與住址；匿名面欄位維持現行最小集。
- 提供封鎖、檢舉（使用者／球局／訊息）、離開群組、取消參加。
- 第一版不強制記錄實際出席或放鳥，不做扣分處罰；既有「打成了」與出席確認 RPC **保留為非強制一鍵輕問**（球局結束後在群組資訊卡與我的球局露出），供結果層指標，不阻斷任何流程。
- 天氣不設欄位；臨時狀況由群組溝通與取消流程處理。

## 第一階段驗證

### 核心假設

台北市的網球玩家會發起或加入符合時間、地點與程度條件的球局，並讓球局達到所需人數。

### 成功定義

- **成局＝名額湊滿（全員 accepted 滿員）**；候選球場局另需**定案**才計成局（避免「湊滿但從未定案」灌水）。
- 成局率按場地類型**分開呈現**（等場局天然帶「不保證有場」折價，混算會系統性高估）。
- 「真的打成」層：以非強制一鍵輕問（打成了／出席）收集，不設回報義務，不作為成局分母條件。
- 量化門檻沿用既有 MVP 設計的精神（首波：20 位真實使用者、8 個真實球局、3 次成功加入、至少 1 次回報打成），上線前於 mvp-plan 定稿。

### 觀察指標

- 發局數、球局數（分場地類型）、加入數、成局率（分型）。
- 再次發局或加入（最強留存訊號）。
- 群聊活躍度：有訊息往來的球局佔比（驗證群聊投資）。
- 球場訂閱數。（~~推播點擊數~~：2026-08-04 確認目前方案量不到，理由見「深連結」節；不列為指標。）
- 在線分享開啟數、目錄 opt-in 數、球友卡邀請數（拍板 3 的觀察項）。
- 各球場、時段與 NTRP 區間的成局差異。
