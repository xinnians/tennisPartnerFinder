# 資訊架構重整與文案統一設計（2026-08-06）

## 背景與目的

首次公開發布的功能管線（Stage 1-6）已完成，hosted 已部署並通過 QA，發布卡在種子球局劇本。
在發布前的使用者走查中，擁有者以使用者身分提出八項困惑；對照 2026-08-06 的全 surface 盤點
（23 個 surface、303 個項目），這些困惑收斂成兩類問題：

1. **東西放錯房間**：12 項設定有 11 項住在「我的球局」頁（79 項，佔全站 26%）；
   全站沒有任何「你是誰」的顯示；個人檔案只在 gate 攔截時打得開，通過 gate 後無法再編輯。
2. **選項比需求多**：開球局表單第一題用內部語彙（「場地類型」）提問；打法四選有兩個界線模糊；
   訂閱球場用 53 座的原生多選；LINE 過渡面在群聊上線後成為第二套並存的聯絡模型。

本設計處理這兩類問題，並順手收斂全站用詞。**不含視覺風格改版**——視覺留待有真實使用者後再談，
本次只修三個具體的對比度／字級缺陷。

### 決策來源

2026-08-06 擁有者逐題拍板（八項困惑 + 三項後續確認）。設計草案於同日確認。

## 一、主結構：新增「我」分頁

### 現況

底部導覽三格（找球局／開球局／我的球局）。header 五項，含與底部重複的「開球局」「我的球局」。
「我的球局」一頁承載九種東西：行動清單、四組設定、封鎖清單、LINE 聯絡、工具列（含全站唯一登出）、
iOS 提示、即將打球、過去紀錄。聯絡支援與隱私權政策以浮動膠囊常駐在地圖左下。

### 目標

底部導覽四格：**找球局 / 開球局 / 我的球局 / 我**。

**「我」頁**（新增）承載：

| 區塊 | 內容 | 來源 |
| --- | --- | --- |
| 身分卡 | Google 頭像、暱稱、NTRP、登出 | 新增（頭像現僅出現在檔案表單預覽） |
| 個人檔案 | 「編輯個人檔案」常駐入口 | 新增入口，沿用既有 sheet |
| 球友卡 | opt-in 目錄開關 | 自「我的球局」7d 搬入 |
| 在線狀態 | 在線分享開關、接受現場問候、定位狀態提示 | 自「我的球局」7e 搬入 |
| 通知 | 開啟推播、六個事件偏好、訂閱球場、iOS 提示 | 自「我的球局」7f 搬入 |
| 封鎖清單 | 已封鎖對象與解除封鎖 | 自「我的球局」7g 搬入 |
| 站務 | 聯絡支援、隱私權政策 | 自地圖浮動膠囊搬入 |

**「我的球局」頁**（瘦身）只留：需要你處理、即將打球、過去紀錄、重新整理。

### 約束與決策

- **分頁命名為「我」**，非「我的」——與「我的球局」並列時必須可區分。
- **「我」頁匿名可進**：未登入顯示登入邀請與隱私權政策連結。這是隱私政策搬離常駐位置的前提，
  匿名訪客仍須找得到它。
- **header 瘦身**：移除「開球局」「我的球局」兩顆（底部導覽已有），保留品牌、城市標籤、使用我的位置。
- **個人檔案 sheet 沿用同一支實作**，新增非 gate 模式：常駐入口進入時不顯示「完成後即可繼續」眉標
  與 gate 提示句，其餘欄位與驗證不變。gate 攔截路徑的行為完全保留。
- 推播是裝置級設定，其餘為帳號級；在線圖層開關是單次瀏覽的檢視狀態，留在地圖頁不搬。
  「我」頁的通知區需標明推播的裝置級語意。

## 二、開球局表單

### 2.1 第一題改問處境

現況第一題為「場地類型」，三個選項是內部語彙（已訂場／現場等場／候選局），要求使用者先理解三個名詞。

改為 **「場地確定了嗎？」**，三個選項改以使用者處境陳述，各附一句說明：

| 值（不變） | 新標籤 | 說明句 |
| --- | --- | --- |
| `booked` | 已訂好場地 | 時間與球場都確定了。 |
| `walk_on` | 球場確定，但要現場排隊 | 公共球場現場輪流，人到齊不保證馬上有場地。 |
| `candidates` | 還沒確定，先列候選 | 先列 2–3 座候選球場與時間範圍，之後再定案通知大家。 |

資料庫的 `venue_type` 三值與所有 RPC 完全不動。這是提問方式與說明文字的改動。

### 2.2 打法收斂為三種

`sessions.play_type` 的 CHECK 約束保留四值（`單打／雙打／對拉／練球`），**資料庫不動**。
前端新開局的選項移除「對拉」，剩單打／雙打／練球，各附一句說明。
地圖篩選同步移除「對拉」chip。

既有「對拉」球局的資料與顯示不受影響（僅 QA 資料，無真實使用者）。

### 2.3 缺額改為按鈕

上限維持 1–3（資料庫約束不動）。`<select>` 改為三顆並排按鈕，減少一次點擊；
補文案「不含你自己」，說明缺額語意。編輯球局表單同步。

## 三、LINE 過渡面退役

群聊已上線且為拍板的聯絡模型，LINE 是舊模型殘留。目前 0 真實使用者，無存量資料要照顧，
現在退役成本最低；保留則須同時維護兩套聯絡模型，並持續把新使用者導向即將消失的功能。

### 移除範圍（前端與文件）

- 個人檔案表單的「LINE ID（選填）」欄位與其揭露 hint。
- 「我的球局」的「已核准的聯絡方式」整區：對方暱稱、LINE ID readonly 欄、複製 LINE ID、
  複製開場訊息、複製狀態與 contacts 錯誤／重試。
- `src/dataApi.js` 的 `loadSessionContacts` 與 `session_contacts` 查詢；`src/main.js` 的接線；
  controller 的 contacts 載入與 refresh 路徑。
- 所有提及 LINE 的 UI 文案（暱稱揭露聲明、profile 揭露句、建局加入方式 hint 等）。
- `public/privacy.html`：移除 LINE ID 的蒐集項、可見性表格列與 callout 段落。
- `CLAUDE.md` 與 `.claude/rules/supabase.md` 的 LINE 過渡面條文改為「已退役」。

### 保留範圍（資料庫）

`public.session_contacts` view、`profiles.line_id` 欄位與既有 RPC **不動**——已凍結的 migration
不可修改，且新增一支 drop migration 對 0 使用者的環境沒有實益。前端不再讀取即達成退役目的。

**技術債登記**：資料庫仍存在無消費者的 LINE 面，未來若做資料清理需一併處理。此項寫入 mvp-plan。

## 四、訂閱球場簡化

現況為 53 座球場的原生 `<select multiple>`，桌機需 Ctrl 點選、行動版進二級選單逐座點。

改為兩段式：

1. 預設呈現單一開關 **「全台北市球場」**（開啟＝訂閱當下所有台北市 active 球場）。
2. 「只訂閱特定球場」展開後，才顯示球場清單（沿用既有 checkbox 樣式 `option-grid`，
   非原生 multi-select），並即時顯示已選數量。

`set_court_subscriptions` RPC 不動：上限已於 202608050001 放寬為當下台北市 active 球場總數，
「全台北市」即傳入全部 id。冷啟動期這也讓新球局廣播能觸及最多人。

## 五、出席回報的用途：中性聚合數

### 現況

`mark_session_played` 將球局設為 `played`；`confirm_session_attendance` 將
`session_participants.played_confirmed` 設為 true。全庫查證：`played_confirmed` 僅由
`my_session_participations` 回傳給本人（`viewer_played_confirmed`），**沒有任何聚合或對外顯示**。
兩者目前是純記錄。

### 目標

讓數字產生用途，作為陌生人之間的信任訊號：

- **主揪**：「已成局 N 次」＝該 profile 作為 host 且 `sessions.status = 'played'` 的球局數。
- **球友**：「已打 N 場」＝該 profile 以 `accepted` 身分且 `played_confirmed = true` 的球局數。

### 隱私邊界（硬約束）

**兩個數字只在登入後可見，不得進入匿名面。**
`public.session_discovery` 的主揪欄位是已拍板凍結的 allowlist，只有 `host_nickname`、
`host_ntrp`、`host_profile_complete`，本設計不擴充。

揭露位置限於既有的 authenticated-only 面：

| 數字 | 承載 view | 顯示位置 |
| --- | --- | --- |
| 主揪已成局 N 次 | 新增欄位於 `public.session_join_preview`（已 `where auth.uid() is not null`） | 球局詳情的加入前名單、加入確認 dialog |
| 球友已打 N 場 | 新增欄位於 `public.player_directory`（已為 authenticated-only 且套 directory gate） | 球友卡、球友名單列 |

### 實作約束

- 新 migration `202608060001`（001-008 與 202608050001 皆已凍結，其中 202608050001 已套用 hosted）。
- 兩個 view 均為有序 allowlist，新增欄位必須置於既有欄位之後，並同步 `src/dataApi.js` 的欄位常數。
- 計數以子查詢或 lateral join 取得；不新增觸發器、不新增快取欄位。
- pgTAP 須涵蓋：匿名對兩個 view 仍無 SELECT 權限、計數正確（0／1／多）、
  `session_discovery` 欄位數與內容未變（防止數字外洩到匿名面）。
- 呈現為中性事實，不是評分：顯示「已成局 3 次」，不顯示比率、星等或排名。N=0 時不顯示該行。

## 六、文案統一：定詞表

同一概念全站只用一種說法。搬家與表單改動時一併套用。

| 概念 | 統一用詞 | 取代 |
| --- | --- | --- |
| 主揪拒絕申請 | 婉拒 | 「未被接受」（推播 body）、「未加入」（角色標籤）、「這次參與未成立」（歷史原因） |
| 尚有名額 | 缺 N 位 | 「剩 N 位」、「缺額」（表單標籤除外，該處指欄位名） |
| 可加入狀態 | 開放加入 | 「開放報名」 |
| 第二人稱 | 你 | 「您」（`ALREADY_REQUESTED` 為全站唯一一處） |
| 個人檔案完整度 | 資料完整 | 「檔案已完成」「檔案待完成」 |

另補一句 NTRP 說明（全站目前零解釋），置於個人檔案 NTRP 欄位與建局的適合程度欄位下方：
「NTRP 是網球程度自評分級：1.0 初學、2.5 能來回對打、3.5 能穩定控球、4.5 以上具比賽水準。」

推播文案的「未被接受」改動需新 migration 修改 enqueue 字串，併入 202608060001。
