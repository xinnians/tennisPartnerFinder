# 空站到朋友加入：球局分享改善提案

日期：2026-09-11。狀態：分享首批已核可並完成本機實作，見[實作規格](native-session-share-2026-09-11.md)；驗證與部署以progress為準。其他段落保留為歷史提案。使用者要延伸討論如何讓進站者主動帶朋友一起用；不是代發訊息或匯入聯絡人的授權。

## 已確認範圍（2026-09-11）

- 使用者同意開局成功後增加分享功能；入口採中性的「分享球局」，不特別強調「邀朋友一起打」，適用分享給個人或群組。
- 第3點格式初步確認。實作含義是調整現有 `sessionShareSummary` 產生的摘要文字，讓「複製球局摘要」與新增系統分享使用同一份內容及 `/s/:id`，不建立兩套格式或新的邀請／成員機制。
- 「分享球局」由本人點擊開啟支援裝置的分享選單；「複製球局摘要」將同一份文字放入剪貼簿，未自動送出。沒有支援或遇到可恢復錯誤時可自行選擇複製，取消不強制複製。
- 本段優先於下方原先以「邀朋友」為主的提案語氣；開局後入口已獲同意，不再標成整批未核可。此次為範圍與文字格式確認，runtime尚未實作，其他空狀態／私人局／獎勵提案不連帶啟動。

### 最新實作決定

本人點「分享球局」直接開系統分享選單，不新增站內選單；系統是否含複製由裝置決定。無原生支援則複製；取消不複製。成功畫面與主揪卡提供入口，詳情保留明確複製摘要。以下原提案的雙主入口／邀朋友文案不作為本批UI規格。

## 核心假設

用戶有一場本來就想打的球，球咖幫他把安排變成清楚的邀請，朋友點開就能理解並回應。邀人的直接收益是這一場比較容易約起來；網站使用者總量在此時可以暫時不是主要判斷依據。

只看匿名公開球局為零，無法推論「全站沒人在用」；時間、範圍與篩選都可能影響結果。產品仍須如實呈現空結果，不能用假球局／假人數製造熱鬧，也不能只靠文案解決真實供給不足。

分享的必要條件是使用者有可分享的真實安排或有用內容、有合適的收件對象，且朋友加入後能得到價值。完全沒有球友可邀的人不能被要求替平台招募。

## 兩種空站使用者

### 有朋友可邀，也有打球意圖

空狀態提案：

> 這個範圍暫時沒有可加入的球局。
> 有想一起打的朋友嗎？建立一場公開球局，把時間、場地和名額整理成連結，再傳給對方。

主動作：「開一局，邀朋友打球」；次動作沿用訂閱／擴大範圍／清除篩選，不額外插入阻擋式問卷或自動顯示分享彈窗。

沿用已有開局表單與原門檻；登入、暱稱和程度需求事先清楚說明。無登入草稿是另外的 G08 選項，不假裝目前已有，也不把它當本批依賴。

### 暫時沒有球友可邀

保留球場訂閱與查場地價值，讓本人選擇想收到的球場通知；無符合球局就如實顯示。若願意主揪，仍可建立真實公開局，但不保證有人報名。依既有 opt-in 規則提供球友目錄，不要求上傳私人群組或通訊錄。

若大量來訪者屬於此類，單靠分享功能仍有上限。需要另以公開主揪教學、真實活動分享或自願參與者建立供給，不能把找不到人的責任轉給使用者。

## 建局成功後的具體畫面提案

只有建立 RPC 確認成功且識別到本人新局後才顯示：

> 球局已建立
> 可分享這場球局，或複製球局摘要。
>
> ［這一局的時間、場地、玩法、程度及剩餘名額］
>
> ［分享球局］ ［複製球局摘要］

可在同一頁處理，保留建立後焦點回復與新局定位。推播授權仍自願，調整呈現時機不能把新申請通知功能撤掉或讓主揪看不見待處理申請。

有缺額才用補人文案；額滿可分享安排，但不要再說「還缺人」。已取消／過期則顯示原權威狀態。建立失敗、網路錯誤、帳號切換或舊成功回傳不得產生假邀請。

## 邀請內容如何讓人願意傳

可以讓已確認身分的主揪在分享預覽中看到「想約一場網球，一起打嗎？」的固定引言，再接現有 allowlist 摘要。參加者或匿名轉分享使用「這場網球有人在找球友」，且僅用仍有缺額的適用狀態；不能讓別人的球局被包裝成自己主揪。

示意訊息（下列變數是提案佔位，非真實球局）：

> 想約一場網球，一起打嗎？
> ［台北日期時間］｜［球場／未定案狀態］
> ［玩法］｜［程度］｜［缺額／狀態］
> 場地狀態：［已訂場／現場等場／候選未定案］
> 最新名額與加入方式看這裡：［這一局的 /s/:id］

不自動加入備註全文、私人聯絡、成員姓名或聊天；分享只讓本人選擇收件人。現有摘要欄位已受G04規格限制，若增添內容需另記 spec。邀請語氣可以溫和，無需「幫我支持新平台」或拉人獎勵。

手機可使用 Web Share API 呼叫系統選單，支援與目標 App 視裝置而定，不承諾一定顯示 LINE；不支援時保留複製。須本人點擊觸發；關閉選單視為取消，不跳錯誤、不自動改為複製或再次彈出。傳給系統分享目標不等於已送達朋友。[MDN 說明](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share)

## 朋友收到連結之後

沿用 `/s/:id` 直達該局，先呈現具體時間、場地、玩法、程度與狀態。匿名可看允許公開的活動資訊；加入前告知登入與必要個人檔案，OAuth 返回同一局，不繞回空白探索頁。

依現有 join matrix，主動作明示「申請加入」或對應直接加入語意；直接加入遇未填／不符程度仍需依規則送申請，不能宣稱所有熟人一鍵免審核。私密加入前名單仍登入後才可讀。accepted 前不開群聊，也不只為轉換放寬容量、封鎖或資料權限。

朋友完成 accepted 後，清楚顯示自己已加入；若還有缺額，可提供不阻擋的「也邀一位球友」選項。不能強制邀人才能看資訊或完成加入；朋友不該承擔主揪尚未批准的加入承諾。

目前球局是公開局。將連結私傳朋友不會變成私人局，也不保留特定人的位置。建局說明必須讓主揪知道這一點。若主要需求是只限熟人的私人安排，需另立產品／權限決策；不能將「連結知道者才看得到」當作已實作安全邊界。

## 讓使用者有第二次理由

真實加入／出席與重開的價值，比複製次數更關鍵。打完後主揪可沿用「照這局再開」，選新日期、重新確認場地，再分享新連結；已加入的人不自動成為新局成員，舊群聊不跨局搬移。

若仍須朋友在站內外重複回覆很多次，就要減少重複工作。網站價值要由更新後的名額、加入狀態、局內協調及下次重開體現。若單純兩人用一句訊息就約好了，本工具未必有額外價值，不應強迫對方註冊來完成本可更簡單的安排。

## 建議實作順序

1. **首批核心（已確認方向）**：建局成功後的「分享球局」入口＋本人觸發的手機系統分享／複製fallback，調整並共用現有公開摘要，沿用逐局文字預覽。不強調邀朋友。
2. **同批必要驗收**：收件者 `/s/:id` → 登入／個人檔案 → 加入或申請 → accepted 的真實手機旅程；有問題就先修，不能只測分享按鈕。
3. **第二批**：空結果用途文案、分享入口位置及成功後再邀提示，按實際摩擦安排。這是G05局部新提案，不自動恢復整批首頁改版。
4. **後續才評估**：逐局圖片、匿名草稿、私人局、時間投票、小團再邀、獎勵制度。它們牽涉不同需求與權限，不一次納入。

首批開局成功分享方向已獲使用者同意，摘要格式初步確認。後續依上述最新範圍補最小spec與實作；不要將其他提案當成本批授權，也不要對已同意的入口重複詢問。

## 如何知道分享真的有用

先區分公開宣傳帶進站、球局分享帶朋友加入、文章轉傳三種行為。

| 要觀察什麼 | 定義與限制 |
| --- | --- |
| 建局後有多少人嘗試分享 | 新局主揪中點擊分享／成功複製的人數及分母，系統選單完成／取消另列；都不當作已傳給朋友 |
| 分享連結是否被開啟 | 同一局的有效到訪，排除可辨識預覽爬蟲／QA；重複到訪需去重。沒有量測時填未知，不用raw HTTP請求當人數 |
| 首位非主揪是否加入 | 建立後第一位非主揪accepted的局數與耗時，按仍有合理開打前觀察窗分組；排除已取消／測試影響，不把requested當accepted |
| 是否真的來自分享 | 需要可用來源或自願回報；同一公開局也可能自然被找到，因此第一位guest加入本身不證明分享因果 |
| 是否持續有用 | 非創辦人重開、下一局非主揪accepted／打成回報，配合完整觀察窗；並列主揪跨工具協調成本 |

最小成功線索是非創辦人自行開局、朋友透過連結完成加入、之後主揪願意再用。第一階段不定虛構轉換率／viral coefficient，不把所有新註冊視作新供給；招募名額已於2026-09-11改為具體正整數（見[人數規格](session-capacity-2026-09-11.md)），但名額增加不等於會有轉傳或加入，仍須觀察實際行為。

量測須另規劃最小事件與去重，無聊天、聯絡人、raw GPS，且不依賴現有Analytics自動提供完整歸因。本輪不新增SDK或修改公開URL。
